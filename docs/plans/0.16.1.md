# keel v2 0.16.1 — native mode: keel without Docker

Plan only. It builds on 0.16.0 (and 0.15.9: keel's file history lives in `data/keel.db`, so a native
`backup` / `restore` carries it too). Line numbers are from v0.15.7.

Goal: `keel2 start --native [dir]` runs keel on this computer with no Docker and no sudo. Docker stays the
default and the safer choice.

## What runs today (the image)

`docker/keel-start` (the image's entrypoint, `Dockerfile:96,106`):

```
keel-start
 ├─ KEEL_INTERNAL_TOKEN  (random when not set, :5)
 ├─ engine   keel-engine on 127.0.0.1:8090           (uv venv /opt/engine/.venv, :28)
 │           waits for GET /health                    (:31-35)
 └─ api      java -jar /opt/api/app.jar on :8080      (Java 21, :37)
             ├─ serves the web app (built into the jar, Dockerfile:32)
             └─ KEEL_DATA, KEEL_WORKSPACE, KEEL_CONTENT, KEEL_FOLDERS, KEEL_ENGINE_URL, KEEL_API_URL
```

Paths hardcoded for the image (they need a native value or a fallback):

- `engine/keel_engine/config.py:47` workspace `/workspace`; `:51-55` content `/opt/keel-v2/content`.
- `engine/keel_engine/runtime/service.py:620-626` (moved projects map `/workspace/...`).
- `api/.../common/KeelProperties.kt:25` `/opt/keel-v1-optional`; `:54-55` content; `:59` `ENGINE_PYTHON =
  /opt/engine/.venv/bin/python` (the agents' keel MCP server, `McpService.kt:80`).
- `docker/keel-start:9` writes `$HOME/.claude.json`. Natively that is the person's own file: **must not**.
- The image sets `git config --system user.name keel` and `safe.directory '*'` (`Dockerfile:71-72`).
  Natively keel must not change the person's git config; keel's commits already pass the author per
  commit (`runtime/actions.py:441-463`).

## 1. Layout on disk

```
~/.keel2/<KEEL_NAME>/                 (default name keel-v2; KEEL_HOME2 overrides the base)
├─ app/<version>/                     one folder per version: api.jar, engine/ (venv), content/, VERSION
├─ current -> app/<version>           the version that runs
├─ data/                              KEEL_DATA: keel.db, master.key, CLI homes, logs of flows
├─ npm/                               agent CLIs and codegraph (npm --prefix), on keel's PATH only
├─ run/engine.pid, run/api.pid, run/ports
└─ logs/engine.log, logs/api.log      rotated at start (keep the last 5)
```

The folders list stays where it is (`${XDG_CONFIG_HOME:-~/.config}/keel2/<name>.folders`, `keel2:193`).

## 2. Getting keel (jar + engine + content)

Two ways:

| | build from source | download a release asset |
|---|---|---|
| needs | git, JDK 21, Node 20 (web build), uv | Java 21 runtime, uv (or python 3.12) |
| time | minutes (gradle + npm) | seconds |
| same as the image | only if the same lockfiles | yes, built by CI from the same tag |

**Recommended: download a release asset.** `docker.yml` already builds on every `v*` tag (`docker.yml:10-11`).
Add a job that uploads `keel-v2-<version>-native.tar.gz` (api.jar with the web app, the engine wheel +
`uv.lock`, `content/`, `VERSION`, sha256) to the GitHub release. `keel2` downloads it, checks the sha256, and
runs `uv sync --frozen` into `app/<version>/engine/.venv`. Building from source stays as
`keel2 start --native --from-source <checkout>` for developers.

Needed on the computer: Java 21 (`java -version`), uv (or it installs uv to `~/.keel2/bin` with the official
installer and `INSTALLER_NO_MODIFY_PATH=1`, like `Dockerfile:83`), git, Node 20 + npm for the agent CLIs.
`keel2 doctor --native` checks all of them and prints the install command for mac (brew) and Linux.

## 4. keel2 in native mode

A new `native` part in `keel2`; every command checks the mode (a file `~/.keel2/<name>/mode`, or a running
container) and calls the Docker or the native code.

| command | native |
|---|---|
| `start --native [dir]` | get the version (if missing), npm CLIs, then start the engine and the api with `nohup`, pid files, wait for `/api/health`; refuse when a Docker keel with the same name runs |
| `stop` | TERM both pids, wait, KILL after 20 s; the "agents are working" question stays (`guard_busy`) |
| `restart` | stop + start with the saved project and options |
| `status` | pids alive, port, version, project, folders, "mode: native" |
| `logs` | `tail -F logs/engine.log logs/api.log` |
| `doctor` | Java, uv, git, node/npm, the CLIs, the port, write access to `~/.keel2` |
| `update` | download the newest release into `app/<new>/`, switch `current`, restart; keep the old one for `keel2 update --rollback` |
| `mcp` | `exec ~/.keel2/<name>/current/engine/.venv/bin/python -m keel_engine.mcp …` with `KEEL_API_URL=http://127.0.0.1:<port>` and the token from `run/` (no `docker exec`, `keel2:585`) |
| `add` / `remove` / `folders` | the same list; natively nothing is mounted, so `KEEL_FOLDERS` is just the list (keel still only looks in these folders) |
| `token`, `tokens`, `sql`, `backup`, `restore` | the same api calls; JSON built with the engine's python instead of `docker exec` (`keel2:506,509,515`); `sql` opens `data/keel.db`; backup tars `data/` |
| `open`, `uninstall` | the same; `uninstall --all` removes `~/.keel2/<name>` after a yes |

- Ports: the api on `PORT` (default 8080, busy → next free, as today); the engine on a free port from 8090
  (`KEEL_ENGINE_PORT`, `config.py:42`), saved in `run/ports`. Both bind 127.0.0.1 only.
- `KEEL_WORKSPACE` = the main project folder; `KEEL_FOLDERS` = main + added; `KEEL_CONTENT` =
  `current/content`; `KEEL_MCP_PYTHON` = `current/engine/.venv/bin/python` (so `KeelProperties.kt:59` is not
  used); `KEEL_INTERNAL_TOKEN` random per start, saved with mode 600 in `run/`.
- A new `keel-start` mode (or `scripts/keel-native-start`) shares the start logic with `docker/keel-start`,
  minus the `$HOME/.claude.json` line and the Docker-socket part.

## 5. What `--docker` means natively

In the container, `--docker` mounts the host's Docker socket so tests can start containers. Natively the
tests already run on this computer and use its Docker if there is one, so `--docker` is not needed:
`keel2 start --native --docker` prints "native mode already uses this computer's Docker" and goes on.
`TESTCONTAINERS_HOST_OVERRIDE` (`docker/keel-start:13`) is **not** set natively.

## 6. The warning

At the first `start --native` (and in `status`, `doctor`, the web app's header as a small badge):

> Native mode: keel's agents run as you, with your files, your SSH keys and your network. In Docker they only
> see the project folders. Docker stays the default; use native mode only on a computer and projects you trust.

The first start asks `[y/N]` (or `--yes`). keel's guard still refuses edits outside the phase rules, but it
is not a sandbox.

## Risks

- **Safety**: agents run as the person and can read anything they can (SSH keys, other repos, cloud
  credentials in env). Docker stays the default; the warning and the `[y/N]` are required.
- The env passed to agents: `safe_env` (`models/cli.py:103`) already drops secrets, but natively the
  person's shell env has many more (cloud tokens). The allowlist must stay an allowlist.
- Java / uv / Node versions differ per computer. `doctor` must say exactly what is missing.
- Two keels (Docker and native) with the same name, or the same port. `start` refuses, with the fix.
- Process cleanup: an agent CLI child may outlive the engine. Kill the process group on stop.
- macOS: Gatekeeper and quarantine do not apply to a jar and a venv, but a downloaded `uv` binary may need
  `xattr -d com.apple.quarantine`. Prefer the official installer (it handles it).
- Windows is out of scope (WSL works as Linux).

## Open questions (with a recommended answer)

1. Build from source or download? **Download the release tarball**; `--from-source` for developers.
2. Where do the files go? **`~/.keel2/<name>/`**, one folder per keel, so a second keel never mixes data.
3. Install missing tools (Java, Node) for the person? **No**: only uv (to `~/.keel2/bin`); `doctor` prints the
   brew / apt command for the rest. No sudo, ever.
4. Agent CLIs: share the person's own installs? **No**: keel's own copies under `npm/`, pinned like the image,
   so a flow behaves the same in Docker and native.
5. Move data between Docker and native? **Yes, through `keel2 backup` / `keel2 restore`** (same tgz format);
   no automatic sync.
6. Should native mode run an agent CLI under a separate OS user for safety? **Not in 0.16.1** (it needs sudo);
   note it as a later idea.

## Report (built 2026-10-14)

Built on `claude/feat-0158-layouts-3be3e8` (one commit, after `611d7d8`). Where reality differed from the plan:

- **uv is required, not installed by keel2**: `native_need` checks Java 21, uv, git and curl and prints the brew / apt
  line; keel2 installs nothing system-wide and never runs sudo.
- **The start script** is a separate `docker/keel-native-start` (bash 3.2 on macOS has no `wait -n`, so it watches
  both processes in a loop) instead of a mode of `docker/keel-start`.
- **Agent homes**: claude and codex already had private homes under `$KEEL_DATA`; copilot and opencode did not. With
  `KEEL_NATIVE=1` every agent CLI gets `HOME` and the `XDG_*` folders under `$KEEL_DATA/agent-home/home`.
- **The tarball** carries the engine's source with `uv.lock` (not a wheel); `uv sync --frozen` builds the venv on
  install. The api is built from a copy of `api/`, because `api/src/main/resources/static/index.html` is tracked and
  must stay untouched.
- The CI job and the release upload are written but have not run (no push from here). The release upload attaches
  to an existing GitHub release of the tag, else keeps the files as the run's artifact (keel does not create
  releases by itself).
- `KEEL_NATIVE_CLIS=0` skips installing the agent CLIs (used by the checks and CI, which run on the fake model).
- The web header badge for native mode was not built; `keel2 status` and `doctor` say it, and the first start asks.

Tests: engine **826 passed, 8 skipped** (new: native agent home); api **200**; web **415/415**; `bash -n` and
`shellcheck -S error` clean for `keel2`, `docker/keel-native-start`, `scripts/build-native.sh`; both workflow files
parse.

Real check (this Mac, `KEEL_HOME2` in a scratch folder, `KEEL_NAME=keel-native-lab`, port 8098; Docker not used):
`scripts/build-native.sh` made a 42 MB tarball and left the checkout clean; `keel2 start --native --from-tarball …`
warned, installed 0.16.1 (uv sync), started; `status` said "running natively" with version 0.16.1; the project was
registered; `keel2 mcp` listed the read tools and `keel_status` answered; `doctor` found no problems; `backup` wrote
a `.tgz`; `stop` left no process; the home folder had the same entries before and after and `~/.keel2` was never
created. A second start with the fake model allowed ran a feature flow to its first gate natively and wrote
`.keel/specs/scores.md`. `uninstall --all` removed the keel folder; the scratch folders were removed.

Open:
- The agent CLIs' npm install was not exercised (skipped for speed); `doctor` reports when they are missing.
- `keel2 update` downloads from the GitHub release, which exists only once a version is released with the new job;
  until then `--from-tarball` / `--from-source` are the ways in.

## Follow-up after the review (2026-10-15)

Done (each with tests):
- **The api checks MCP levels itself** (`c7768c8`, branch feat/api-levels): three in-memory tokens (read, write, admin),
  handed out by `POST /api/mcp/token` only with the internal token; keel's MCP server sends its level's token as
  `X-Keel-Mcp-Token`; a request that says it is MCP (or carries a token) is refused above its level (403 "This needs the
  MCP write level: run keel2 mcp --write"); `/actions` always needs a token; agents get no internal token, so they act at
  read. In Docker, `keel-start` writes the internal token to `/data/run/internal-token` (600) for `keel2 mcp`.
- **An automated test for native `update` and `--rollback`** (`55444c6`): `scripts/test-keel2-native.sh` with fake
  releases over `file://` (install, update, "newest already", a tampered checksum refused, rollback both ways); in CI.
- **The native badge** in the web header (`health.native`) and **"Two versions — pick one"** for a file two flows wrote
  (`conflict` state, diff of both, keep either) (`a697eb9`).
- **Real checks again on the final code** (keel-lab, cleaned up): the three layouts and the unseen link; a diff of
  `/etc/passwd` refused (400); a new project in `.keel/`, a flow to its spec gate, history, `rm` → `missing` at once
  (the empty-answer glitch is gone), Restore back as version 2 by the user, no file text in `events`.

Still open:
- The api has no login. A local process that does not say it is MCP is treated like the web app (full access), and an
  agent running as the same OS user can read the internal token file. Closing that needs a login or separate users.
- The `/api/mcp-servers` write routes stay at the write level (maybe admin).
- The stop-and-restart path of native `update` is not covered by the automated test (it needs Java and a running keel).
