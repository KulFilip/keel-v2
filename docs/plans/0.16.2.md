## Decisions (open questions, each with the answer used)

| # | Question | Answer used |
|---|---|---|
| 1 | Rules page under Settings or Build? | **Build › Rules**, next to Workflows: it is "how agents work". Settings stays for the DB values. |
| 2 | Where do installed and own rule packs live? | **In the project: `.keel/rules/<id>.yaml`.** `load_config` reads them, so the hook, the ToolBox and the diff guard all get them with no engine-specific code, a running flow sees a change at the next tool call, and the team shares them through git (layout keel/external: .keel/ is outside git, still in the folder). Workflows are in the DB because the engine gets them at start; rules must be read on every tool call. |
| 3 | Where is the library? | `content/rules/*.yaml` (shipped in the image, `KEEL_CONTENT`), listed by the engine. |
| 4 | How does the Rules page change `.keel/config.yml`? | The engine rewrites only the top-level blocks it owns (`guards`, `mcp`, `rules`, `boundaries`), keeps every other line as it is. Comments inside those blocks are lost; the page says so. No new YAML library. |
| 5 | Can an agent switch the rules off by editing `.keel/config.yml` or `.keel/rules/`? | Today yes (bucket `other`, allowed in most phases). **New bucket `keel-rules`**: `.keel/config.yml` and `.keel/rules/**` are always refused to agents (like `.env`), except `.keel/config.yml` in phase `setup` (init writes it). Same bucket in `KeelRules.kt`. |
| 6 | Which built-in rules can be switched off? | Off is allowed: `read-build-output`, `generated`, `skip-test-flags` (`-x test`, `-x check`), `new-dependency`, `read-twice`, `big-file-read` (= `read_guard_max_lines: 0`), `push-gate`, `mcp-writes`. **Never off**: `.env` protection (read, print, edit), force push, `--no-verify`, `git commit` in a flow, `reset --hard` / `rebase -i`, existing migrations, the phase matrix, `keel-rules` files, secrets at write time, disabled-test markers. The API and the engine both refuse to switch off a never-off rule. |
| 7 | Codex: what can block before the action? | Codex 0.160 has stable `hooks` with a Claude-shaped `PreToolUse` (tool_name/tool_input, exit 2 = blocked; strings in the 0.160 binary) and `--dangerously-bypass-hook-trust` "for automation that already vets hook sources" (keel writes the hook itself). keel passes the hook with `-c hooks.PreToolUse=[…]` when `codex --version` ≥ 0.150 (cached), plus the **command wrappers** (8). Older codex: wrappers + diff guard, and the "checked after each step" note. |
| 8 | Copilot: what can block before the action? | Copilot has no hook keel can load without writing into the project (`.github/hooks`). keel gives it **command wrappers**: a folder first on the agent's PATH with `git`, `gh`, `npm`, `pnpm`, `yarn`, `bun`, `pip`, `pip3`, `uv`, `poetry`, `cargo`, `go`, `gem`, `cat`, `head`, `tail`, `less`, `more` that ask the same hook (`Bash` + the command) and then run the real tool. Its own file edits stay "after the step only": the UI says so. A wrapper is not a sandbox (an agent can call `/usr/bin/git`); the diff guard stays the backstop. |
| 9 | Push gate in the hook: the hook must stay light (no DB). | The engine computes `push_blockers` when an agent starts and writes them into the guard context (`push_blockers: [{gate, why, fix}]`); nothing that changes them (verify steps, keel commits) runs during an agent run. The hook and the ToolBox refuse `git push` / `gh pr create` (`rules.push_gate_commands`) while the list is not empty, only when `.keel/config.yml` exists (keel v1 rule). keel's own push action is engine code and is not an agent call: it keeps working. Off: `rules.push_gate: false`. |
| 10 | Secrets and disabled-test markers at write time: a PreToolUse hook has no file yet. | Check the **new text** in the call: Write `content`, Edit `new_string`, MultiEdit `edits[].new_string`, opencode `content`/`newString`, ToolBox `write_file`. After the step the diff guard scans the added lines of every changed file (all engines) and puts the file back. Skipped: generated/build paths, `.env.example`, lines with `keel:allow-secret`; markers only in test files. |
| 11 | `read_guard_max_lines` default? | **2000** (Claude's own Read stops at 2000 lines; a bigger file read whole wastes tokens). 0 = off. A read with offset or limit always passes. |
| 12 | Recording a failed shell command: `last_failure`? | Not `state.last_failure`: the compiler uses it for `retry_only` steps and run modes (compiler.py L273, run_mode.py L161), so an agent's failed `ls` would change the flow. The runners report the last failed command in `AgentResult.data["failed_command"]`; the compiler keeps it as `data.last_command_failure` {step, agent, command, output} and emits it on `agent.finished`. Explain and "Rules now" show it. |
| 13 | Re-ask when a result marker is missing | Once per agent per step attempt, for registered markers with values (BLOCKING, REPRO, …) that the step declares: the same agent again (its session continues where the provider can), with "repeat your full answer and end with `NAME: a | b`" (keel v1 subagent-stop: a reply that only says the marker would lose the findings). Still missing: the step goes on as today. |
| 14 | Fail-closed: keep the read-only exception? | **Keep.** With no readable context a read changes nothing, `.env` and build output stay blocked by the defaults, and refusing reads too would only make the agent fail with no useful signal. Writes, shell, MCP: refused. Documented in GUIDE and CONTRACT. |
| 15 | Settings "keel rules" (Settings.kt L18/L49, Settings.tsx L43) is read by nothing. | **Remove it.** The real switch is per workflow (`workflows.keel_rules`, validate.py L244-263). An old saved value is ignored (`Settings` ignores unknown keys). |
| 16 | Dry-run "which recent tool calls would this have blocked" | The API reads the project's last 500 `agent.step` events (tool, write, edit, read; with the phase from that call's `agent.started`) from its `events` table and sends them with the pack to the engine, which runs only the pack's rules on each call. |
| 17 | MCP levels | `keel_rules` read. `keel_rule_install` and `keel_rule_edit` (add, change, remove, switch a built-in) **admin** with confirm: they change what agents may do. |

## Rule pack format

```yaml
id: no-new-dependencies          # file name .keel/rules/<id>.yaml; [a-z0-9-]
name: No new dependencies
description: Agents never add a package; a person does.
rules:
  - id: no-install               # unique in the pack
    kind: bash                   # bash | edit | read | mcp
    match: [npm install, pnpm add, yarn add, pip install, uv add]
    how: contains                # contains (bash default) | regex | glob (edit/read default) | name (mcp default)
    phases: all                  # all | in-flow | none (outside a flow) | [green, refactor, ...]
    lanes: [web]                 # optional: only in this lane (red/green)
    except: ["**/package-lock.json"]   # optional (edit/read): these paths pass
    reason: Adding a package is a person's decision.
```

A pack rule only refuses (never allows what keel refuses). Every engine path uses it through `rules.check_*`.
An unlock ("allow this file in this phase") passes an edit rule too, like the matrix.

Shipped packs (`content/rules/`): `strict-secrets`, `no-new-dependencies`, `migrations-only-in-flow`,
`frontend-not-api`, `stack-spring` (Gradle wrapper, `application-prod*`), `stack-node` (lockfiles by hand,
`.npmrc`), `stack-python` (`uv.lock`/`poetry.lock` by hand, `.python-version`).

## Risks

- Codex hook: the input shape is read from the 0.160 binary, not seen live (a live codex call on this Mac needs the trust-bypass flag, which this session may not run). The hook normalises several tool names; the diff guard stays the backstop. Open item: one live codex run in keel-lab with a codex login.
- Wrappers slow every `cat`/`git` of codex/copilot by a Python start (~50 ms).
- Big-file rule at 2000 lines may refuse reads agents did before; the reason says how to read a range.
- The config block rewrite drops comments inside `guards`/`mcp`/`rules`/`boundaries`.
- New bucket `keel-rules` changes classify for `.keel/config.yml` (was `other`): commit rules for `setup` keep it (setupOnly paths), the api's repo view shows the new bucket.
