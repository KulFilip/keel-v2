## 1. keel v1 layouts

keel v1 0.79 (`lib/layout.js`) reads `layout:` from `.keel/config.yml`:

| layout     | specs                               | knowledge         | adr          | runbook            | CLAUDE block       |
|------------|-------------------------------------|-------------------|--------------|--------------------|--------------------|
| `repo`     | `specs.dir`, else `docs/specs` or `specs` | `docs/knowledge` (`memory.dir`) | `docs/adr` | `docs/RUNNING.md` (`setup.runbook`) | `CLAUDE.md` |
| `keel`     | `.keel/specs`                       | `.keel/knowledge` | `.keel/adr`  | `.keel/RUNNING.md` | `.keel/CLAUDE.md`  |
| `external` | same as `keel`; `.keel` is a symlink to `~/.keel/projects/<id>/` |  |  |  |  |

`repo` is the default when the key is missing or unknown. In `keel` and `external`, `.keel/` is hidden
from git through `.git/info/exclude`.

### Resolver (one per side, same rules)

- New `engine/keel_engine/layout.py`: `raw_config(root)`, `resolve(root, cfg=None) -> Layout`.
- New `api/src/main/kotlin/keel/api/knowledge/Layout.kt`: `Layout.resolve(root: Path)`.
- `Layout` has:
  - `name`
  - the write paths: `specs`, `knowledge`, `adr`, `runbook`, `claude`
  - the read lists: `spec_dirs`, `knowledge_dirs`, `adr_dirs`, `runbooks`. Each list starts with the
    layout's own folder, then every other known folder that exists. So a mixed project (the user's
    ludus-engine has both `.keel/specs` and `docs/specs`) shows both.
  - `link` (where `.keel` points) and `missing` (the message when the link target is not visible)
  - `hidden` = name is not `repo`
  - `knowledge_file(section)`: the layout's own file, else one in another knowledge folder
- Repo default for specs: `specs.dir` only when the config sets it. Note: the engine's `DEFAULT_CONFIG`
  says `specs`, so the resolver must read the raw file, not the merged config.
- External: `.keel` is a symlink. The config sits behind the link, so when the target is not visible
  the layout is still `external`, with `missing` set.

## 2. external layout whose target keel cannot see

- `Layout.missing` = "this project keeps keel's files in <target>; add that folder too: keel2 add <target>".
- The app shows it on the Wiki and on Files keel wrote (see above).
- `keel2` `cmd_add` (`:345-370`): for each new folder (and each repo one level down, like
  `register_added` `:215-238`), if `<repo>/.keel` is a symlink, read its target. If the target is not
  inside the main project, an added folder, or the folders being added now: `warn` with the same
  sentence.
- Mounts (`keel2:279-304`): `--docker` mounts the project at the same path; without it the main
  project is `/workspace`, so an absolute link from the main project only works if the target is
  added with `keel2 add`. Added folders are mounted at the same path in both modes.

## Risks

- `load_config` now sets `specs.dir` from the layout. A repo project without `specs/` gets
  `docs/specs`, so the guard starts refusing `docs/specs` edits in red / green / gate. This is what we
  want, but it changes behaviour, and some engine tests may expect `docs/specs` to be "other".
- `load_config(root)` runs often. The resolver does a few `stat` calls and reads the config once; fine,
  but do not read the config twice.
- Hidden layouts: `.keel/` is git-excluded, so `git add` of a spec there fails or stages nothing. The
  spec gate, the memory verdict and the setup step must treat "recorded" as success.
- Knowledge "stale" uses git history; a hidden layout never has any, so stale never shows there.
- An absolute symlink target is only visible when it is mounted at the same path. Without `--docker`,
  a relative link inside `/workspace` works, an absolute one only after `keel2 add <target>`.
- `#/projects/<id>/…` must not break the `projects` page itself (`#/projects` with no id).

   `specs.dir` if set, else whichever of `docs/specs` / `specs` exists, else `docs/specs` (no change
   for v2 users). OK?
2. Hidden layout commits: record and continue (like keel v1), or ask the user once per flow? Plan:

3. Should keel v2 also *write* the layout (`.git/info/exclude`, the `CLAUDE.local.md` import, moving
   files like `keel upgrade --layout`)? Plan: no — 0.15.8 only reads layouts that keel v1 set up.
4. `keel_start_flow` with a dirty tree or the fake model: the API refuses (409) like the web. Should
   the tool take `allow_dirty` / `allow_fake`? Plan: no flags in 0.15.8; the error text says what to do.
   For the real check on the fake model this needs `props.fakeOnRealProjects` set in keel-lab.
5. `keel_dashboard` without `keel2 mcp` (an agent inside keel): it falls back to the API URL, which is
   the container's port. Good enough, or should the API expose its public URL (`keel.public-url`,
   `application.yml:38`) in `/api/health` so the tool can read it?
