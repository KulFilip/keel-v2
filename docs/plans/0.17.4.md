# keel v2 0.17.4 — criteria order, the amendment loop, Java test names

An urgent fix from a real run (ludus-engine, keel 0.17.3, feature flow, run mode important; 1.49M tokens, 0/7 criteria
done). Branch `fix/0.17.4-order-loop` from `origin/main` 51edea1. Line numbers are from that commit.

## What went wrong

```
spec Plan: **ORDER**: AC-006, AC-002, AC-007, AC-001, …
keel ran : AC-001 first (id order)
red AC-001 ─► AMEND "needs PluginDescriptorLoader from AC-006/002/007"
   ─► amend explorer: "REOPEN: none — execution-order issue, not a spec defect"   (spec unchanged)
   ─► amend_gate shows the spec's LAST amendment block (an old one) ─► approve ─► "Nothing to commit"
   ─► back to red AC-001 ─► the same AMEND  … 4 times
before that: green AC-006 failed: -Dtest=*AC-006* can never match a Java class (AC006PluginSubstrateRegressionTest)
```

Causes in the code:

1. `spec_sync` (runtime/feature_actions.py L180-199) takes the order only from the plan agent's last-line marker
   `ORDER:`; the spec's own Plan line (`**ORDER**: …`, which the person reads and may edit at the gate) is ignored.
2. `spec_amend_commit` (L321) re-sorts the criteria in the spec's listing order: an amendment undoes any order.
3. `rules.gate_due` (rules/__init__.py L681) finds the lane's last criterion by sorted id, not build order.
4. The amendment path has no memory: `amend_start` (L255) always sends to the explorer, `spec_amendment` (L290)
   shows the spec's last block even when this round wrote none, and the gate cannot say "this is an order problem".
5. Test filters: `{AC}` gives `AC-006`; a Java class or method name cannot hold a dash. Maven is not detected at all
   (testcmd.py `detected` knows gradlew only). `ran_no_tests` does not know Surefire's messages.
6. MCP `keel_status` / `keel_next` cut text mid-word and show a choice gate as approve / reject.

## Fix

1. **ORDER** (`feature_actions.spec_order`): the spec's `ORDER:` line (plain, bold, in a list; in the Plan or
   anywhere) wins, else the plan agent's marker. Listed ids first in that order, the rest after in id order. The
   order lives in `state.acs` (the loop takes the first unfinished one), so a resume keeps it; `data.ac_order =
   {ids, from: spec | plan | person}` says where it came from. `spec_amend_commit` keeps the current order (new
   criteria at the end, or where ORDER puts them). `gate_due` uses the list order. Flow page criteria panel: "build
   order" with its source; MCP `keel_status`: an `Order:` line.
2. **Amendment loop guard**:
   - `spec_amendment` sees whether this round changed the spec (`git diff HEAD -- <spec>` empty = no change). No
     change → no approve-only gate:
     - the explorer (or the AMEND line) names unfinished criteria, or says it is an order question and ORDER lists an
       unfinished criterion before this one → **reorder automatically** (those first), say so in the gate log and the
       timeline, back to red for the first of them;
     - otherwise → the **choice gate** `amend_loop`.
   - `amend_start` remembers each round (`data.amend_history`): the same criterion back with an AMEND after a round
     that changed nothing goes straight to `amend_loop` (no explorer, no tokens).
   - `amend_loop` choices: `first` (do <the next criterion> first), `skip` (move <AC> to the end), `edit` (the
     amendment again, with your note), `stop` (stop the flow). Every choice changes something.
3. **Java-safe test names**: placeholder `{AC_ID}` (AC-006 → AC006) next to `{AC}` / `{AC_KEY}`. A Maven `-Dtest=`
   or Gradle `--tests` filter with `{AC}` also matches the dash-free id (`-Dtest='*AC-006*,*AC006*'`, a second
   `--tests`). Maven detected (`mvnw` / `pom.xml`): `-Dtest='*{AC_ID}*'`. The red prompt names the exact test name the
   filter finds (Java/Kotlin: `AC006…` in the class or method name). `ran_no_tests` knows "No tests were executed",
   "No tests matching pattern", "No tests to run", Gradle's "No tests found for given includes".
4. **MCP text**: cut at a word boundary with "…"; a gate with named choices lists them (name: what it does).

## Tests

Engine: spec ORDER parsing (bold, list, plain, partial), spec_sync order + source, amend commit keeps order,
gate_due by list order; the loop guard (auto reorder; choice gate on the second round; first / skip / edit / stop);
`{AC_ID}`, the Maven/Gradle filter widening, Maven detection, Surefire no-test messages, the red prompt text; MCP
status text (word cut, choices, Order line). Web: the criteria panel shows the build order.

Real check: throw-away keel (`KEEL_NAME=keel-lab KEEL_VOLUME=keel-lab-data PORT=8097 KEEL_OPEN=0`, own
`XDG_CONFIG_HOME`), a tiny Java/Maven scratch project with a spec that has ORDER, fake model: the order is followed,
the loop guard fires once with choices, an `AC006…` test is found by the filter. Then everything removed.

## Risks

- A spec line starting `ORDER:` that is not meant as the build order: only AC ids in it are read, unknown ids ignored.
- Reordering moves criteria the person approved in another order: the gate log and the timeline say so, and the
  choice gate is shown when keel cannot tell.

## Outcome (2026-10-16)

Built as planned (commits on `fix/0.17.4-order-loop`). Real check (keel-lab on 8097, volume keel-lab-data, a Java/Maven
scratch project, model `fake-lab`): the spec gate said "in build order (from the spec's ORDER line)" and AC-2 ran
before AC-1; AC-1's AMEND got one explorer round that changed nothing, then the choice gate (skip / edit / stop; no
"first" because nothing else was unfinished); `skip` brought AC-1's AMEND back straight to the choice gate (the explorer
ran once in total), `stop` stopped the flow with the note. `keel_status` showed `order AC-2 → AC-1 (from the spec's
ORDER line)` and the choices. In the container with Maven 3.9.9: keel ran `mvn -q test -Dtest=*AC-006*,*AC006*` (exit 0,
`demo.AC006RankTest`: 1 test run), while the 0.17.3 filter `-Dtest=*AC-006*` failed with "No tests matching pattern",
which keel now reads as "no test ran". Everything removed afterwards.

Open: the gate lists `first` even when nothing else is unfinished (the text and MCP leave it out; choosing it moves the
criterion to the end, like skip).
