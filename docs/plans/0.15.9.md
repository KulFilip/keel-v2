# keel v2 0.15.9 — keel's file history in the database, and `.keel/` by default

Plan only. It builds on 0.15.8 (the layout resolver). Line numbers are from v0.15.7.

## Why a separate version (not in 0.15.8)

- 0.15.8 is about reading files where they are (layouts, errors, two MCP tools). This is a new feature with
  its own migration, events, endpoints and screens: about as big as 0.15.8 again.
- The migration number matters for the plugin track (below); one migration per release is easier to merge.
- The user's default (`.keel/` for new projects) is only safe once this history exists, because `.keel/` is
  not in git. So the switch for new projects is **on in 0.15.9**, together with the history. 0.15.8 already has
  the rule in the resolver; 0.15.9 turns on its last branch ("no key, no keel files → `keel`") and makes init
  write `layout: keel` (`runtime/actions.py:486-510`).
- If the user wants one release: build 0.15.8 and 0.15.9 on the same branch and release them as one.

## Goal

Per project, keel's database keeps:

1. **Every version of every spec** keel creates (and of the knowledge sections, ADRs and runbook): content,
   hash, flow and thread, phase and step, who changed it (agent, KeelBot, the person, MCP, keel itself), when,
   and the git commit if there is one.
2. **What keel applied on top of the repo**, per flow: the branch and worktree it made, the commits it made,
   and the files it wrote that are not in git (in `.keel/`).

So the history survives without git, the app can show a spec's versions and a diff, and a deleted or
overwritten spec can be put back.

```
 agent / KeelBot / keel action writes .keel/specs/x.md
        │
 engine: after each step, compare keel's files with the last snapshot
        │  changed → event doc.version {path, kind, sha256, content, by, thread, step, phase}
        ▼
 POST /internal/events  ──►  api EventService.apply  ──►  doc_versions (row per version)
                                                    └──►  flow_applied (commits, branch, worktree, files)
 web: Wiki › spec › History (versions, diff, restore)   ·   Flow › "What keel applied"
```

## 1. Migration `V15__doc_history.sql` (next after `V14__thread_hidden.sql`)

```sql
CREATE TABLE doc_versions (
  id          TEXT PRIMARY KEY,          -- dv-<uuid8>
  project_id  TEXT NOT NULL,
  path        TEXT NOT NULL,             -- relative to the project root, e.g. .keel/specs/scores.md
  kind        TEXT NOT NULL,             -- spec | knowledge | adr | runbook
  version     INTEGER NOT NULL,          -- 1, 2, 3 … per (project_id, path)
  sha256      TEXT NOT NULL,
  content     TEXT,                      -- NULL for a deletion, and over the size limit (then only the hash)
  size        INTEGER NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0,
  by_kind     TEXT NOT NULL,             -- agent | keelbot | user | mcp | keel | outside
  by_name     TEXT,                      -- explorer, librarian, "Claude Code", …
  thread_id   TEXT, step TEXT, phase TEXT,
  commit_sha  TEXT,                      -- filled when the file is in a keel commit (repo layout)
  at          TEXT NOT NULL,
  UNIQUE (project_id, path, version)
);
CREATE INDEX doc_versions_path ON doc_versions(project_id, path, version DESC);
CREATE INDEX doc_versions_thread ON doc_versions(thread_id);

CREATE TABLE flow_applied (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id  TEXT NOT NULL,
  thread_id   TEXT NOT NULL,
  kind        TEXT NOT NULL,             -- branch | worktree | commit | file | recorded
  ref         TEXT NOT NULL,             -- branch name, worktree name, sha, or path
  subject     TEXT,                      -- the commit message, or the step's note
  files_json  TEXT,                      -- a commit's files
  at          TEXT NOT NULL
);
CREATE INDEX flow_applied_thread ON flow_applied(thread_id, at);
```

- **Plugin track:** `plugin-base` already has its own `V15__approvals.sql` (never released). Main's released
  migrations keep their numbers, so when the track merges 0.15.9 its approvals migration becomes `V16`
  (the track's sessions do this, with an upgrade test from 0.15.9's history). This plan never touches
  plugin-base.
- Size: content up to 512 KB is stored (a spec is a few KB). Bigger: hash only, `content` NULL.

## 2. Where it is written

### Engine (new `runtime/doc_history.py`)

- `snapshot(root) -> {path: sha256}` over the layout's files: every `spec_dirs` `*.md`, the knowledge
  sections, `adr_dirs` `*.md`, the runbook (0.15.8 `layout.resolve`).
- The compiler's step runner (`runtime/compiler.py:240-250`, around `fn(i, step, …)`): snapshot before the
  step, again after it; for each new, changed or deleted file emit `doc.version` with `{path, kind, sha256,
  content, deleted, by_kind, by_name, step, phase}`. `by` comes from the step: an agent step → `agent` +
  the agent's name; a code step → `keel` + the action name. A flow started via MCP (0.15.8 `started_via`) keeps
  `by_kind: agent` and adds `via: mcp`.
- Snapshot once at flow start (`runtime/service.py:266-300`): a file that changed since the last known
  version and before this flow is recorded as `by_kind: outside` (the person, or another tool).
- KeelBot (`runtime/helper.py`): the same before / after around a Fix turn; `by_kind: keelbot`.
- Commits: `runtime/actions.py:398-405` (after `git commit`) emits `keel.applied {kind: commit, sha, subject,
  files}`; for every staged keel file the api fills `commit_sha` on its newest version. KeelBot's
  `helper.commit` (`runtime/helper.py:431`) is mapped the same way. A hidden-layout "recorded, not committed"
  (0.15.8) emits `keel.applied {kind: recorded, files}`.
- Branch and worktree: the api makes them (`FlowService.start`, `ownBranch` / `worktreeFor`,
  `FlowService.kt:218-225`), so the api writes those rows itself after the thread id is known (`:238-245`).
- The event bus already buffers and retries when the api is down (`events/__init__.py`); a large content is
  one event, under the 512 KB limit.

### API

- `events/EventService.kt:56` `apply`: new cases `doc.version` (insert with the next `version`, skip when the
  sha equals the newest version's) and `keel.applied` (insert into `flow_applied`; for a commit, set
  `commit_sha` on the matching newest versions).
- New `knowledge/DocHistoryService.kt` + `DocHistoryController.kt`.

## 3. Endpoints (`/api/projects/{pid}/…`)

| method | path | returns |
|---|---|---|
| GET | `/docs/history` | every tracked file: path, kind, versions, newest `at`, state `ok` / `changed outside keel` / `missing` |
| GET | `/docs/history/versions?path=` | one file's versions (no content): version, sha, by, thread, phase, commit, at |
| GET | `/docs/history/versions/{id}` | one version with content |
| GET | `/docs/history/diff?path=&from=&to=` | a unified diff between two versions (`to` may be `file`, the file on disk) |
| POST | `/docs/history/restore` `{versionId}` | writes that content to the file; the restore is a new version `by_kind: user` |
| GET | `/api/threads/{tid}/applied` | what this flow applied: branch, worktree, commits (with files), keel files written |

- `path` must be one the layout knows (inside `spec_dirs`, `knowledge_dirs`, `adr_dirs`, the runbook): no `..`,
  no other file. Restore refuses while a flow runs or waits **in the same folder** and is in red, green or a
  gate (the spec is frozen there; an amendment is the way); the error says so.
- CONTRACT v0.15.9 lists them.

## 4. Web

- Wiki spec page (0.15.8 `spec:` pages, `pages/Wiki.tsx`): a **History** tab: the version list (version, who,
  flow, phase, when, commit) and a diff of two picked versions (reuse the review diff view,
  `components/review/ReviewDiff.tsx`). The same tab for knowledge sections, ADRs and the runbook.
- A file that is missing on disk but has versions shows "missing — Restore version N" (a button with a
  confirm). A file changed outside keel shows "changed outside keel" with a diff to the last known version.
- Files keel wrote (`pages/repo/KeelView.tsx:139-163`): the same states as pills; missing files are listed
  too (from the history), with Restore.
- Flow page: a **What keel applied** panel from `/threads/{tid}/applied`.

## 5. DB vs file: who wins

- **The file is the source of truth for the current text.** The database is history only. keel never
  overwrites a file from the database by itself.
- File differs from the newest version → it is recorded as a new version `by_kind: outside` (at the next
  snapshot, or when the history page is opened), never "fixed".
- File missing and versions exist → state `missing`; the app offers Restore; nothing happens automatically.
- Both a worktree and the main folder changed the same spec (0.15.8 copies back on flow end): both are
  versions; the main folder's file stays; the copy-back writes the worktree's text only when the main file did
  not change since the flow started, else it shows "two versions — pick one" (a restore of either).

## 6. `.keel/` default switch (from 0.15.8)

- `layout.resolve`: "no `layout:` key, no keel files in `docs/`, `.keel` not a link" → `keel`
  (engine `layout.py`, api `Layout.kt`; one line each plus tests).
- `write_config` (`runtime/actions.py:500-510`): writes `layout: keel` for a new project, `layout: repo` when
  keel files are in `docs/` already; `.git/info/exclude` lines for `keel` (0.15.8 helper).
- The init plan text (`runtime/init_gates.py:85-106`) names the layout so the person can change it at the gate.

## Risks

- Database growth: every knowledge refresh rewrites six files. Small (KBs), but keep an eye on it; a cleanup
  setting (keep the last N versions of knowledge) is a later idea. Specs are kept forever.
- Secrets in a spec: the content goes into keel's database (on the data volume, in backups). Run the same
  secret check as commits (`checks.secrets_in_diff`) and store masked lines.
- Snapshots on every step cost a few `stat` + hash calls; only keel's folders are read, never the whole tree.
- `by_kind: outside` can be wrong when two keels share a folder (rare); it is a label.
- The event carries file content through the internal endpoint; it stays on 127.0.0.1 with the internal token.

## Open questions (with a recommended answer)

1. One release with 0.15.8, or two? **Two plans, one branch**; release them together if the user wants the
   `.keel/` default at once.
2. Track knowledge, ADRs and the runbook too, or only specs? **All four**: they are all outside git in `keel`.
3. Keep history in `repo` layout too (git has it already)? **Yes**: one code path, and the app's History tab
   works the same everywhere; `commit_sha` links to git.
4. Restore while a flow runs? **Refused in red, green and gates** for that folder; allowed otherwise.
5. Show the history through MCP? **Yes, in 0.16.0**: `keel_specs` gets `history: true` (read) and
   `keel_restore_doc` (write, with a confirm).
