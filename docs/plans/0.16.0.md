# keel v2 0.16.0 — full MCP: read, --write, --admin

Plan only. It builds on 0.15.8 (`keel_dashboard`, `keel_start_flow`, layouts) and 0.15.9 (the file history,
`.keel/` by default). Line numbers are from v0.15.7.

Goal: a person's own Claude Code (or Claude Desktop, or another MCP client) can do from the chat what the
dashboard does, at the level the person chose. Agents inside keel stay read-only.

## Levels

```
keel2 mcp              read     look at everything, change nothing (default; what agents get)
keel2 mcp --write      + write  decide gates, answer questions, start flows, git / PR / CI / DB writes
keel2 mcp --admin      + admin  stop flows, delete runs, add / remove projects, edit workflows
         --allow a,b   only these tools (on top of the level)
         --yes         no confirm prompt when the client cannot show one (see Safety)
```

Each level includes the one below. A tool that is not in the level is **not registered**, so the client cannot
see it (the same rule as today, `mcp_server.py:524`).

## 2. Safety

- **Levels and allowlist**: `write_mode` (`mcp_server.py:571`) becomes `level(argv) -> "read" | "write" |
  "admin"`. `--read-only` still wins over everything (agents). `KEEL_MCP_WRITE=1` stays as write;
  new `KEEL_MCP_LEVEL`. `--allow t1,t2` (and `KEEL_MCP_ALLOW`) registers only the named tools that are in the
  level; an unknown name is an error at start.
- **Agents stay read-only**: `tools/mcp.py:23` and `api/.../mcp/McpService.kt:182` keep `--read-only`;
  `McpService.kt:124` already refuses changing the keel server's command. Test both.
- **Confirm before risky calls (MCP elicitation)**: push, DB change, delete run, stop flow, remove project,
  edit workflow, and admin actions. The `mcp` package is 1.30.0 (`uv.lock`), which has `Context.elicit`.
  - Default: always ask.
  - If the client cannot elicit (`ctx.session.client_params.capabilities.elicitation` is empty): refuse,
    with "this client cannot ask you to confirm; run keel2 mcp with --yes to allow it without asking".
  - `--yes`: no prompt. The plugins' own "ask in keel's Inbox" (`_ask_person`, `mcp_server.py:409`) stays,
    as a second check for git / DB / CI.
- **Recorded in the timeline**: every write and admin call sends `X-Keel-Via: mcp` and
  `X-Keel-Client: <clientInfo.name>` (`KeelApi` `mcp_server.py:41-69`). A new api filter
  (`api/.../mcp/McpAudit.kt`) records each mutating request with that header as an event `mcp.call`
  `{tool, client, path, result}` on the project (and thread when there is one), through `EventService`
  (`events/EventService.kt`). `web/src/components/events.ts` shows "via MCP · <client>: <tool>". The 0.15.8
  `thread.started.via` becomes the same thing.
- **No secrets through MCP**:
  - no tool calls `/api/secrets`, `/api/connections` values, logins or plugin keys;
  - `keel_read_file` and `keel_search` refuse secret files. **Gap found:** `repo/file` (`RepoService.file`)
    (`RepoService.kt:247`) and `repo/raw` (`:285`) do not check `RepoService.isSecret` (`:550`); only search does (`RepoSearch.kt:111,160`).
    Fix it in the api for everyone, and check it again in the MCP tool;
  - `keel_db_query` keeps masking secret columns (`mask: True`, `:359`);
  - tool output goes through `checks.secrets_in_diff`-style redaction before it is returned.
- **Guard rules apply to everything**: the tools call the api, and the api runs the same rules as the
  dashboard (no force push, no push to main or master, readonly run mode, the phase matrix). No tool runs a
  shell command.

## Risks

- `keel_run_action` outside a flow: many actions read flow state (`acs`, `base`, `spec`). A blank
  `ActionInput` can make them fail in odd ways. That is why only a short list is allowed outside a flow.
- Many tools make a long `tools/list`; clients put the descriptions in every prompt. Keep descriptions
  short; `--allow` helps.
- Elicitation support differs between clients and versions. The safe default (refuse) may feel strict.
- `X-Keel-Client` is the client's own claim, so it is a label, not proof of who called.
- Remove project: keel has no delete today, only `hidden` (used for eval projects,
  `ProjectService.kt:144-154`) and parked roots. Reusing `hidden` keeps the history, but the project
  disappears from every list.

## Open questions (with a recommended answer)

1. Should `--admin` include `--write`? **Yes**: each level includes the one below.
2. When the client cannot elicit: refuse, or ask in keel's Inbox? **Refuse, unless `--yes`**, as asked.
   The Inbox ask stays for git / DB / CI as a second check.
3. `keel_remove_project`: delete the row or hide it? **Hide it** (`hidden = 1`), keep its history; adding the
   same root again shows it again.
4. `keel_run_action` outside a flow: a short allowlist, or every action? **Short allowlist**, the rest only
   inside a flow (they still show in `keel_actions`, marked flow-only).
5. Workflow edits through MCP: full YAML or small changes? **Full YAML through `PUT /workflows/{wid}`, after
   `POST /workflows/check`**, and only for the project's own workflows (built-in ones are copied first, like
   the web does).
6. Should keel record read calls too? **No**: only write and admin calls go to the timeline; reads would
   flood it.
